# 自動部署指令使用步驟手冊

## 目的

完成一個可部署版本後，使用 Git Tag 指令啟動 Staging 自動部署。一般 Commit／Push 只保存程式，不會部署；只有首次推送符合格式的新部署 Tag 才會觸發。

本手冊適用於興趣專案的 Staging，不包含 Production。

## 先選操作入口：部署新版本，或切換已發布版本

### 控制台網址與可做的操作

版本控制台在本機啟動後，從這裡開啟：

**[開啟版本控制台](http://127.0.0.1:4190/)**

若連結無法開啟，先在 Repository 根目錄執行：

```bash
cd platform/release-console
npm start
```

控制台可查看各 Staging 專案的 current／previous、已驗證版本及部署紀錄；可選擇一個 verified Release 部署，或回退 previous。它會透過 GitHub Actions 執行切換，完成 Smoke 後才更新 current／previous；不是直接上傳檔案的頁面。

這是 `127.0.0.1` 本機網址，只能在啟動控制台的同一台電腦開啟，**不是公開或平板可直接連線的網址**。需要已登入且有權限的 GitHub CLI（`gh`）、允許操作的帳號，以及可讀取 Staging 狀態的 Wrangler 登入。控制台不提供任意 Commit／Branch 部署、Release 刪除或 Production 操作。

### 什麼時候用 Tag，什麼時候用控制台

- **發布剛完成的新程式**：先 Commit／Push，再建立全新的 `dep_<project>_v<版本>` Tag，走下方自動部署流程。
- **切換到已發布的版本**：用上方控制台部署 verified Release 或回退 previous；不要重推舊 Tag。

## 可部署專案與 Tag 格式

| 專案 | Tag 格式 | Staging 網址 |
|---|---|---|
| `game-demo` | `dep_game-demo_v版本號` | <https://game-demo-staging.takoson68.workers.dev/> |
| `dinecore` | `dep_dinecore_v版本號` | 由專案操作手冊確認 |
| `project-b` | `dep_project-b_v版本號` | 由專案操作手冊確認 |

版本使用三段式 SemVer，例如 `0.1.4`、`1.0.0`；預發布版本可使用 `1.0.0-rc.1`。每個 Tag 只部署一個專案。

## 一次完整部署

以下以 `game-demo` 的 `0.1.5` 為例。每次發布都要換成尚未使用過的新版本號。

### 1. 確認要發布的內容已 Commit

在 Repository 根目錄執行：

```bash
git status --short --branch
git log -1 --oneline
```

確認最新 Commit 就是要發布的版本，而且它已推送到 GitHub。未 Commit 的檔案不會進入部署包。若還有其他未提交修改，先確認哪些屬於本次版本，不要為部署而把不相關檔案一起提交。

```bash
git push origin world-oop
```

等待這個普通 Push 完成即可；普通 Push 不會部署。

### 2. 建立並推送新的部署 Tag

```bash
git tag -a dep_game-demo_v0.1.5 -m "release - game-demo v0.1.5"
git push origin dep_game-demo_v0.1.5
```

其他專案請改用對應的專案名稱，例如 `dep_dinecore_v1.2.0`。Tag 必須指向已在遠端的 Commit，且名稱必須從未使用過。

**不可移動、刪除後重建或重用已發布的部署 Tag。** Workflow 會拒絕非首次建立的 Tag 更新；若同名 GitHub Release 已存在，或無法確認 Release 狀態，會在部署前停止。不要用重推舊 Tag 的方式發布新程式，請增加版本號。

### 3. 等待 GitHub Actions 完成

前往 Repository 的 Actions：

<https://github.com/takoson68/moducore_platform/actions/workflows/deploy-staging.yml>

打開標題含剛才 Tag 的 `Deploy staging` 執行紀錄，等待整體結果為綠色 `success`。必須確認以下步驟成功：

- Tag 首次建立／Release 重用檢查
- 建置、測試與 ZIP 封裝
- 對應 Worker／Static Assets 部署
- 該專案的 Smoke Test
- GitHub Release 建立及部署紀錄保存

失敗或仍在執行時，不要把版本當作已上線，也不要再推同名 Tag。先打開失敗步驟讀取原因，修正後提高版本號再發布。

成功的 GitHub Release 會附上 ZIP、manifest 與 SHA-256 checksum；版本控制台會以成功的部署紀錄更新 current／previous。

### 4. 立即確認畫面版本

`game-demo` 部署成功後，打開遊戲 Staging 網址：

<https://game-demo-staging.takoson68.workers.dev/>

確認右上角「目前展示版本」膠囊顯示與 Tag 完全相同的版本，例如 Tag 為 `dep_game-demo_v0.1.5`，畫面就應顯示 `v0.1.5`。這是最直接的版本變更確認；只看到 Actions 成功或 HTTP 200 還不算完成畫面驗收。

若原本的分頁仍顯示舊版：

1. 先強制重新整理頁面。
2. 若仍舊，開啟全新分頁；可在網址後加不重複的查詢字串，例如 `?release-check=0.1.5`，再確認版本膠囊。
3. 新分頁仍不一致時，回 Actions 確認建置使用的 Tag／Commit，並檢查遊戲版本膠囊是否等於 Release Tag；不要只以快取中的舊分頁判定部署失敗或成功。

目前已驗收版本 `dep_game-demo_v0.1.4`，畫面顯示 `v0.1.4`，可作為確認操作成功的參考。

## 版本控制台替換版本

需要完整步驟時，依本手冊前方「控制台網址與可做的操作」啟動控制台。選取目標專案的 verified 版本，確認 Project 與 Tag 後執行「部署」；或使用「回退 previous」。等待 Workflow 成功後，再次確認 Staging 網頁版本膠囊。控制台只處理 Staging，不提供 Production。

## 常見狀況

| 狀況 | 處理方式 |
|---|---|
| 普通 Push 後沒有部署 | 正常。要建立並推送新的 `dep_<project>_v<版本>` Tag。 |
| Tag 推送後沒有 Workflow | 檢查 Tag 拼字、專案白名單、版本格式，以及 Tag 指向的 Commit 是否已 Push。 |
| Workflow 拒絕 Tag | 不要移動或重用 Tag；提高版本號並建立新的 Tag。 |
| Actions 成功，但舊分頁顯示舊版本 | 強制重新整理或用全新分頁確認版本膠囊。 |
| Smoke 或測試失敗 | 以失敗 Run 為準，修正後增加版本號重新發布；current／previous 不應因失敗而更新。 |

## 指令速查

```bash
# 查看目前分支、未提交檔案與最新 Commit
git status --short --branch
git log -1 --oneline

# 先推送一般程式 Commit（這一步不會部署）
git push origin world-oop

# 建立並推送全新的部署版本（此步會觸發 Staging 部署）
git tag -a dep_game-demo_v0.1.5 -m "release - game-demo v0.1.5"
git push origin dep_game-demo_v0.1.5
```

執行前請將範例 `0.1.5` 換成下一個未使用版本，並確認 Tag 的 Project 與實際要部署的專案一致。

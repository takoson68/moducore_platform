## Verified Platform Facts

- [container.js](F:/GitHub/moducore_platform/platform/frontend/src/app/container/container.js)
  container 已分成 `coreFactories`、`moduleFactories`、`instances`、`routes`、`listeners`，並提供 `reset()`、`resetModuleFactories()`、`subscribe()`、`emit()`。

- [container.js](F:/GitHub/moducore_platform/platform/frontend/src/app/container/container.js)
  `register(name, factory, { scope })` 已支援 `core` / `module` scope；`core` 重複註冊會 throw，`module` 重複註冊可覆蓋並先 dispose 舊 instance。

- [moduleRuntime.js](F:/GitHub/moducore_platform/platform/frontend/projects/moduleRuntime.js)
  `resolveAllowedNames()` 先處理 `allowList` 與 `isModuleEnabled()`，之後才 `await loader()`；module import 是真正 lazy。

- [register.js](F:/GitHub/moducore_platform/platform/frontend/src/app/container/register.js)
  route registration 已收斂成單一 `resolvedRoutes`；同一份結果同時餵給 `container.registerRoute()` 與 `container.emit('routes-updated', { resolvedRoutes })`。

- [index.js](F:/GitHub/moducore_platform/platform/frontend/src/router/index.js)
  router 已改為訂閱 `subscribeContainer('routes-updated')` 與 `subscribeContainer('routes-reset')`，不再依賴 `window.dispatchEvent`。

- [world.js](F:/GitHub/moducore_platform/platform/frontend/src/world.js)
  `world.reset()`、`world.dispose()` 已建立，`window.__MODUCORE_RESET_WORLD__` 已移除，lifecycle 已回到 world/container。

- [_storeFactory.js](F:/GitHub/moducore_platform/platform/frontend/src/app/stores/_storeFactory.js)
  persistence 已改為 debounce，預設 `80ms`；`set()` 不再同步 storage IO。

- [_storeFactory.js](F:/GitHub/moducore_platform/platform/frontend/src/app/stores/_storeFactory.js)
  已支援 `persistKeys`、`persistDelay`，並以 `sanitizeForPersistence()` 避免 `window`、DOM node、function、循環參照進入 persistence payload。

- [boot.js](F:/GitHub/moducore_platform/platform/frontend/src/app/boot/boot.js)
  boot flow 目前是 `resolveBootVisibility -> registerAllowedModules -> enterRuntime`，module visibility 先決，安裝流程乾淨。

- [world.js](F:/GitHub/moducore_platform/platform/frontend/src/world.js) + [index.js](F:/GitHub/moducore_platform/platform/frontend/src/router/index.js)
  router cleanup 已跟 world lifecycle 綁定，reset/dispose 時可解除 container 事件訂閱。

## Findings

- [container.js](F:/GitHub/moducore_platform/platform/frontend/src/app/container/container.js)
  `unregister(name)` 目前仍可刪 core factory。這給平台自己留了過大的破壞面，最好限制只能移除 module factory。

- [container.js](F:/GitHub/moducore_platform/platform/frontend/src/app/container/container.js)
  事件系統是輕量 `Map -> Set` pub/sub，實用但沒有事件型別約束，也沒有 once / debug trace；規模再大時可觀測性會不足。

- [world.js](F:/GitHub/moducore_platform/platform/frontend/src/world.js)
  `reset()` 會重跑 boot，但不會重建 router 實例；目前靠明確事件同步，這是可用的，但仍比明確 router lifecycle contract 弱一層。

- [_storeFactory.js](F:/GitHub/moducore_platform/platform/frontend/src/app/stores/_storeFactory.js)
  雖已移除同步 storage IO，但 flush 時仍是單次 `JSON.stringify(payload)`；大 payload 在 flush 時仍可能有短暫主執行緒成本。

- [boot.js](F:/GitHub/moducore_platform/platform/frontend/src/app/boot/boot.js)
  `assertPlatformBoundary()`、`initModules()` 仍是空殼 extension point，表示 boot contract 還沒有被完全制度化。

## Inferences

- 平台核心現在已沒有 `window.__MODULE_ROUTES__`、`window.__MODUCORE_RESET_WORLD__`、`window.dispatchEvent('moducore:routes-updated')` 這類關鍵 global coupling。

- 目前平台層的主要風險不再是效能，而是 contract completeness 與未來觀測性。

- 從現況來看，平台核心已可支撐多專案隔離、module lazy install、router/container 一致化，以及可控 reset。

---

## Suggestions

- 在 [container.js](F:/GitHub/moducore_platform/platform/frontend/src/app/container/container.js) 限制 `unregister()` 只能處理 module scope，core factory 應走獨立管理路徑。

- 為 [container.js](F:/GitHub/moducore_platform/platform/frontend/src/app/container/container.js) 的事件系統補事件常數與 debug trace，至少固定 `routes-updated`、`routes-reset`、lifecycle 類事件名。

- 在 [world.js](F:/GitHub/moducore_platform/platform/frontend/src/world.js) 補一層明確 router lifecycle 契約，例如 `rebuildRouter()` 或 route sync policy，避免之後 reset 行為被隱式依賴。

- 為 [_storeFactory.js](F:/GitHub/moducore_platform/platform/frontend/src/app/stores/_storeFactory.js) 加入 persisted payload size guard，超過門檻時直接 warn 或拒絕持久化。

- 把 [boot.js](F:/GitHub/moducore_platform/platform/frontend/src/app/boot/boot.js) 的空 extension point 補成正式 hook contract，避免未來有人在 boot 流程內偷插分叉邏輯。

---

## Final Verdict

1. 平台核心目前是健康的，而且已進入可維護、可擴展狀態。
2. 仍有架構級風險，但已從 global coupling / reset 不乾淨，降到 contract 還可再收斂的等級。
3. 平台下一輪最應修的 3 件事：
   - 限縮 container 的 core/module 管理權限，避免 `unregister()` 誤傷核心。
   - 補強 container observable 與 world lifecycle 的正式 contract。
   - 為 store persistence 加上 payload 邊界與觀測機制，避免未來被大型資料慢慢拖垮。

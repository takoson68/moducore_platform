# Codex 任務：單一專案效能評分（Project Performance Score）

你現在是資深前端效能工程師，請只針對單一專案進行效能檢測與評分，不要把平台核心與其他專案的重量混入。

## 目標
輸出一份針對單一專案的正式效能報告，用來判斷：
- 這個專案目前的載入策略是否合理
- 這個專案是否有明顯效能熱點
- 這個專案是否適合目前的交付方式

---

## 前置條件
執行前必須先確定 `targetProject`。
可接受值：
- dineCore
- flowCenter
- modudesk
- project-a
- project-b

---

## 強制規則
1. 只能分析 `targetProject`
2. 不可把平台核心問題算進專案分數
3. 不可把其他專案的 bundle / asset / route 問題算進本專案
4. 不可以 chunk 拆分數量作為正向加分依據
5. 不可以因為專案採單包或少包輸出就直接扣分
6. 對中型專案應重視少請求、少依賴鏈、交付簡單度
7. 只有在單包已明確過重或大型功能確實拖慢首載時，才可建議拆出獨立 bundle

---

## 評分範圍

### A. Initial Load（25 分）
檢查：
- JS bundle size
- CSS size
- 首頁實際請求數
- FCP / LCP / TTI
- 初始交付策略是否合理

### B. Delivery Simplicity & Request Control（20 分）
檢查：
- 首頁是否只載入必要資源
- 是否存在過多 chunk / 過深依賴鏈
- 是否存在 request waterfall 風險
- 當前交付策略是否符合專案規模

### C. Dependency & Asset Control（20 分）
檢查：
- Chart.js / html2canvas / editor / images / fonts / qrcode 等重依賴
- dead dependency
- mock / config / debug code 是否被正式帶入
- 外部圖片與第三方資源風險

### D. State & Rendering Hotspots（20 分）
檢查：
- 巨型 store
- full-state spread
- 不合理 re-render
- deep clone / JSON clone
- 不當 localStorage persistence

### E. Runtime UX（15 分）
請模擬：
- 100 route switches
- 1000 store updates
- 1000 cards render
- 2000 rows render
- FPS / 體感流暢度

## 輸出格式

[Project Performance Report]

Project: <targetProject>
Score: XX / 100

Breakdown:
- Initial Load: XX/25
- Delivery Simplicity & Request Control: XX/20
- Dependency & Asset Control: XX/20
- State & Rendering: XX/20
- Runtime UX: XX/15

---

Measured Facts:
- JS / CSS / Other
- Delivery shape
- Routes
- Runtime benchmark
- Memory
- FCP / LCP / TTI

---

Verified Code Facts:
- 只列 targetProject 的實際程式碼事實
- 每一點都要附檔案路徑與原因

---

Scoring Guardrail:
- 明確說明本次報告不把 chunk 數量視為載入效能正向依據
- 明確說明是否採單包 / 少包策略，以及這是否符合專案規模

---

Findings:
- 只列 targetProject 的問題
- 若有 store / persistence / request 效能風險，需指出模組與檔案

---

Suggestions:
- 必須可直接實作
- 不可空泛
- 不可以預設「多拆 chunk」就是優化方向

---

Delta:
- Before / After / Delta
- 若本次評分修正了舊有錯誤假設，需明確寫出

---

Final Verdict:
請明確回答：
1. 這個專案目前的交付策略是否合理
2. 這個專案最大的效能風險是什麼
3. 下一輪最應修的 3 件事

---

## 額外要求
1. 若專案違反平台規則，例如模組自行操作 localStorage、full-state spread、未拆分大型 store，需明確標示
2. 若報告使用推估數值，必須註明是 inferred，不可偽裝成真實量測
3. 報告必須重新依當前 build 與當前程式碼檢查，不可沿用舊模板

## 報告產出
- 應產出至本層目錄新增檔案

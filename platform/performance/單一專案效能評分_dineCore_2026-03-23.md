## Scoring Guardrail

- 本報告不以「拆包越多越好」作為正向依據。
- 本報告不把 route / chunk 拆分數量當成載入效能加分項。
- 對 dineCore 這類中型專案，少請求、少依賴鏈、單包或少包交付，視為合理且可加分的交付策略。
- 只有當單包大到明確拖慢首載，或大型功能已證明需要獨立抽離時，才考慮拆出額外 bundle。

---

## Findings

- 現行單包輸出對 dineCore 較合理。以 `452.32 kB raw / 132.44 kB gzip` 的 JS 體積來看，首載成本仍在健康範圍內，沒有明確理由拆成大量 chunk。

- 載入效能的關鍵不在 route 拆得多細，而在少請求與少依賴鏈；目前 `index.html` 只拉 1 支 JS + 1 支 CSS，這比先前大量 chunk 更符合本專案情境。

- 最大熱點仍是 [restaurant-map-editor/store.js](F:/GitHub/moducore_platform/platform/frontend/projects/dineCore/modules/restaurant-map-editor/store.js)。它同時承擔 maps / selection / draft / persistence / sequence，造成高耦合與大範圍更新。

- `restaurant-map-editor` 仍自行做同步 localStorage 寫入，這繞過了平台已優化過的 storeFactory persistence，也違反目前工程規則。

- `mockRequest.js` 與專案內 mock/config 成本仍值得檢查；這不是因為 chunk 數，而是因為正式環境不該帶入不必要執行碼。

- 專案有多處外部圖片來源，首屏體驗會受第三方資源品質影響；這不是 bundle 問題，但是真實 UX 風險。

---

## Suggestions

- 維持 dineCore 的單一 JS / 單一 CSS 輸出，除非之後有明確證據證明某個大型功能必須獨立抽離。

- 優先拆 [restaurant-map-editor/store.js](F:/GitHub/moducore_platform/platform/frontend/projects/dineCore/modules/restaurant-map-editor/store.js) 成 `mapState`、`selectionState`、`draftState`、`persistenceState`，並移除 full-state spread。

- 把 `restaurant-map-editor` 的 `persistDraftState()` / `loadPersistedState()` 收回平台 storeFactory，改走 `persistKeys` + debounce，不要維持模組自管同步 storage。

- 若正式環境不需要 mock，調整 dineCore 的 mock layer 載入條件，避免 [mockRequest.js](F:/GitHub/moducore_platform/platform/frontend/projects/dineCore/api/mockRequest.js) 持續占用執行體積。

- 對 [LayoutRoot.vue](F:/GitHub/moducore_platform/platform/frontend/projects/dineCore/layout/LayoutRoot.vue) 與 [EntryLandingPage.vue](F:/GitHub/moducore_platform/platform/frontend/projects/dineCore/modules/entry/pages/EntryLandingPage.vue) 的外部背景圖加上本地化或更輕量格式，避免第三方資源拖慢真實體感。

## Final Verdict

1. dineCore 目前可運作，且以現行單包交付策略來看，載入方向比先前更符合本專案規模。
2. 最大架構風險不是「拆包不夠」，而是 `restaurant-map-editor` 的單體 store 與自管 persistence。
3. dineCore 下一輪最應修的 3 件事：
   - 拆 `restaurant-map-editor/store.js`
   - 移除 editor 自管同步 localStorage persistence
   - 精簡 mock layer 與外部圖片依賴

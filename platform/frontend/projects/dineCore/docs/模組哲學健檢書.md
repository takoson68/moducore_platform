# dineCore 模組哲學健檢書

更新日期：2026-03-10

## 1. 目的

本文件用來檢查 `platform/frontend/projects/dineCore/modules/` 內現有模組，
是否符合目前專案原始的模組哲學：

- 模組應有明確責任邊界
- 模組不應只是 project shell 的附屬零件
- 模組不應直接依賴其他模組的具體內部狀態
- 跨模組狀態或能力若要取得，必須經由 world / container 的合法入口
- 即使技術上透過 `world.store(...)` 取得，也不代表語意上就已經低耦合

---

## 2. 世界規則對照

依目前 world 文件，跨模組能力與狀態取得的合法邊界是明確存在的。

主要依據：

- [01_WORLD_MODEL.md](/F:/GitHub/moducore_platform/_VibeCore/world/01_WORLD_MODEL.md)
  - `Container 是能力的唯一取得來源`
- [02_WORLD_BOUNDARIES.md](/F:/GitHub/moducore_platform/_VibeCore/world/02_WORLD_BOUNDARIES.md)
  - `Container as the Only Capability Gateway`
  - 禁止模組之間直接 import 業務能力
  - 禁止繞過 Container 取得其他模組能力
- [09_WORLD_RULES.md](/F:/GitHub/moducore_platform/_VibeCore/world/09_WORLD_RULES.md)
  - `Container 是能力存在的唯一合法來源`
  - `container.register` 是能力進入世界的唯一方式
- [01_INVARIANTS.md](/F:/GitHub/moducore_platform/_VibeCore/world/01_INVARIANTS.md)
  - `INV-03 Container 為唯一能力入口`

因此，判斷標準必須分成兩層：

1. 形式層
   - 是否經由 `world` / container 入口取得能力
2. 語意層
   - 是否仍然直接依賴另一個模組的具體 store 名稱、session 結構或內部資料形狀

本次健檢發現：

- dineCore 有不少程式碼在形式層上符合規則，因為它們確實使用了 `world.store(...)`
- 但其中部分實作在語意層上仍然高度耦合，因為它們直接知道別的模組具體 store 名稱與內部資料結構

也就是說，現在的主要問題不是「沒從 world 取得」，
而是「雖然從 world 取得了，但取得的是別的模組具體內臟」。

---

## 3. 健檢判定標準

之後若再次執行模組哲學健檢，應固定使用以下判準，不得臨時更換尺標。

### 3.1 形式層判準

1. 是否經由 `world` / container 入口取得能力或狀態
2. 是否繞過 world / container 直接 import 他模組能力
3. 是否在模組外部直接操作他模組內部檔案或內部資料落點

### 3.2 語意層判準

1. 是否直接知道他模組 store 名稱
2. 是否直接知道他模組 session 結構
3. 是否直接知道他模組資料 shape
4. 是否可在不改他模組內部的前提下替換依賴來源
5. 是否缺少 project-level 抽象服務層
6. 是否把本應屬於 project-level orchestration 的責任塞回模組
7. 是否把本應屬於 module-local 的責任推回 shared layer 或其他模組

### 3.3 判定原則

- 形式層違規：
  - 視為明確違規
- 形式層合規，但語意層高度耦合：
  - 視為偏離模組哲學
- 形式層合規，語意層也僅存在合理流程耦合：
  - 可列為暫時可接受

## 4. 健檢結論

本次盤點後，明確偏離模組哲學的模組有：

1. `staff-auth`
2. `visitor-stats`

邊界偏鬆、已有流程耦合，但目前仍可勉強視為業務模組的有：

1. `menu`
2. `cart`
3. `checkout`
4. `order-tracker`
5. `entry`

其餘目前未看到明確違反模組哲學的證據，但仍受 project shell 與 staff session 架構影響。

## 5. 明確違反

### 5.1 `staff-auth`

判定：**明確違反模組哲學**

原因：

- 它沒有自己的 routes，也沒有自己的 page。
- 它在 `modules/` 內的唯一輸出只有 store。
- 目前真正的登入 UI 與流程控制不在模組內，而在 project shell。

證據：

- [index.js](/F:/GitHub/moducore_platform/platform/frontend/projects/dineCore/modules/staff-auth/index.js)
  - 只註冊 `dineCoreStaffAuthStore`
- [LayoutRoot.vue](/F:/GitHub/moducore_platform/platform/frontend/projects/dineCore/layout/LayoutRoot.vue#L25)
  - 直接抓 `dineCoreStaffAuthStore`
- [LayoutRoot.vue](/F:/GitHub/moducore_platform/platform/frontend/projects/dineCore/layout/LayoutRoot.vue#L294)
  - 由 shell 主動 `loadSession()`
- [LayoutRoot.vue](/F:/GitHub/moducore_platform/platform/frontend/projects/dineCore/layout/LayoutRoot.vue#L347)
  - 由 shell 主動 `login()`
- [LayoutRoot.vue](/F:/GitHub/moducore_platform/platform/frontend/projects/dineCore/layout/LayoutRoot.vue#L358)
  - 由 shell 主動 `logout()`

診斷：

- 這個模組比較像 `project-level staff session adapter`
- 它不是獨立功能模組
- 它更接近 `components/`、`services/`、`stores/` 的 project 共用結構，而不是 `modules/`
- `staff-auth` 的問題不是實作錯，而是命名與放置位置錯
- 它不是不能存在，而是不應以 `modules/` 身分存在

建議方向：

- 將登入 UI 拆到 project-level component
- 將 session 映射拆到 project-level service / store
- 不再以 `staff-auth module` 的名義存在

---

### 5.2 `visitor-stats`

判定：**明確違反模組哲學**

原因：

- 它雖然有 route/page/store，看起來像模組，但內部直接依賴 `staff-auth`
- 它直接讀 `dineCoreStaffAuthStore` 的 session 與 token
- 這表示它不是透過抽象能力取用 staff 身分，而是直接耦合另一個模組實作

證據：

- [VisitorStatsPage.vue](/F:/GitHub/moducore_platform/platform/frontend/projects/dineCore/modules/visitor-stats/pages/VisitorStatsPage.vue#L6)
  - 直接 `world.store('dineCoreStaffAuthStore')`
- [VisitorStatsPage.vue](/F:/GitHub/moducore_platform/platform/frontend/projects/dineCore/modules/visitor-stats/pages/VisitorStatsPage.vue#L11)
  - 直接以 `session.isSuperAdmin` 判斷
- [visitorStatsApi.js](/F:/GitHub/moducore_platform/platform/frontend/projects/dineCore/modules/visitor-stats/api/visitorStatsApi.js#L33)
  - 直接抓 `dineCoreStaffAuthStore`
- [visitorStatsApi.js](/F:/GitHub/moducore_platform/platform/frontend/projects/dineCore/modules/visitor-stats/api/visitorStatsApi.js#L36)
  - 直接讀 `session.token`

形式層判斷：

- 它形式上有經過 `world.store(...)`

語意層判斷：

- 它直接依賴另一個模組具體 store 名稱與 session 結構
- 因此仍然違反原始模組解耦哲學

診斷：

- 這個模組不是靠統一 staff API 邊界工作
- 它直接打穿了 `staff-auth` 模組邊界
- 若未來 staff session 結構調整，`visitor-stats` 會一起壞

建議方向：

- 改吃 project-level permission service
- token 取得統一走 core `tokenStore` / `staffApiRequest`
- 不要直接依賴 `staff-auth` store

## 6. 本次不處理的合理耦合

本專案是流程型產品，不應把所有耦合都視為壞事。
以下耦合目前視為合理且可接受：

1. 同一流程鏈共享 ordering context
2. shell 作為 route / layout orchestration
3. staff dashboard 對聚合 API 的依賴
4. staff shell 對目前 route 狀態、已註冊導航與 layout 呈現的依賴

補充說明：

- 合理耦合不代表可以直接打穿他模組內部 store
- 合理耦合的前提是：
  - 責任清楚
  - 邊界可描述
  - 替換路徑存在
  - 不依賴對方私有內臟

## 7. 邊界偏鬆，但目前仍可接受

### 7.1 `entry` / `menu` / `cart` / `checkout` / `order-tracker`

判定：**流程耦合偏高，但仍可視為同一條顧客點餐鏈上的業務模組**

這一組模組目前的問題不是「完全不像模組」，
而是它們彼此之間的資料流高度互相咬合。

代表性證據：

- [MenuPage.vue](/F:/GitHub/moducore_platform/platform/frontend/projects/dineCore/modules/menu/pages/MenuPage.vue#L8)
  - 直接讀 `menuStore`
- [MenuPage.vue](/F:/GitHub/moducore_platform/platform/frontend/projects/dineCore/modules/menu/pages/MenuPage.vue#L9)
  - 直接讀 `cartStore`
- [MenuPage.vue](/F:/GitHub/moducore_platform/platform/frontend/projects/dineCore/modules/menu/pages/MenuPage.vue#L10)
  - 直接讀 `entryStore`
- [MenuPage.vue](/F:/GitHub/moducore_platform/platform/frontend/projects/dineCore/modules/menu/pages/MenuPage.vue#L47)
  - 直接把 menu 載入結果寫回 cart schema
- [checkout/store.js](/F:/GitHub/moducore_platform/platform/frontend/projects/dineCore/modules/checkout/store.js#L54)
  - checkout store 直接抓 `dineCoreCartStore`
- [checkout/store.js](/F:/GitHub/moducore_platform/platform/frontend/projects/dineCore/modules/checkout/store.js#L84)
  - submit 時再一次直接抓 `dineCoreCartStore`

形式層判斷：

- 這些實作大多有走 `world.store(...)`

語意層判斷：

- 它們直接知道別的模組具體 store 名稱
- 因此仍偏離「只透過抽象能力邊界互動」的理想狀態

診斷：

- 它們比較像「一條顧客點餐流程被拆成多個 page slice」
- 而不是完全獨立、互相不知道彼此存在的模組
- 這種情況在流程型產品中可理解，但已偏離「模組缺席安全」的理想狀態

建議方向：

- 後續若要回到原始模組哲學，應把共享流程狀態往 project-level flow service 收
- 各模組盡量不要互相直接抓 store

補充判斷：

- 這組目前我不列為「立即要拔掉 modules 身分」
- 但屬於應持續警戒的高耦合區

## 9. 非模組但會放大耦合的來源

雖然本文件主題是模組健檢，但本次檢查發現真正放大耦合的核心來源不是單一模組，而是 project shell：

- [LayoutRoot.vue](/F:/GitHub/moducore_platform/platform/frontend/projects/dineCore/layout/LayoutRoot.vue)

它目前直接碰到：

- `entry`
- `cart`
- `menu`
- `staff-auth`

這使得模組雖然分散在 `modules/`，但實際仍被 shell 集中編排。

這不代表 `LayoutRoot` 非法；
但代表如果未來要降低模組耦合，project shell 一定要一起重構。

## 10. 改善規劃

### 10.1 第一階段：先處理明確違反項

目標：

- 把最直接違反模組哲學的結構先收斂

執行項：

1. 將 `staff-auth` 從模組思維改為 project-level 共用能力
2. 將 `visitor-stats` 對 `staff-auth store` 的直接依賴改掉
3. 將 staff token / super admin 判斷收斂到單一 service

完成定義：

- `staff-auth` 不再以 module 名義存在
- `visitor-stats` 不再直接讀 `dineCoreStaffAuthStore`
- staff token / permission 統一由單一 service 提供
- `visitor-stats` 的 route/page/API 不再知道 `staff-auth` 的具體 session shape

完成後可改善到的程度：

- `staff-auth` 不再是假模組
- `visitor-stats` 不再直接知道其他模組 store 名稱
- staff 區的 session / permission 邊界會明顯乾淨很多

仍無法改善的部分：

- `LayoutRoot` 仍會是 staff shell 的主要組裝點
- 顧客流程模組群仍維持高流程耦合

---

### 10.2 第二階段：收斂顧客流程共享狀態

目標：

- 降低 `entry`、`menu`、`cart`、`checkout`、`order-tracker` 彼此直接抓 store 的情況

執行項：

1. 建立 project-level flow service 或 ordering context service
2. 讓顧客流程模組透過 flow service 取得共享狀態
3. 逐步取消跨模組直接抓 `entryStore` / `cartStore`

完成定義：

- `entry/menu/cart/checkout/order-tracker` 不再直接互抓彼此 store
- 共享流程狀態改由 project-level flow service 提供
- 模組之間若需共享狀態，只能透過明確 flow abstraction 或 API truth

完成後可改善到的程度：

- 顧客流程模組仍可保留 modules 身分
- 但共享狀態改由 project-level 流程能力承接
- 模組之間的直接認識程度會下降

仍無法改善的部分：

- 顧客流程本質上仍是一條強流程鏈
- 不可能完全達到「彼此完全不認識」的極端低耦合

---

### 10.3 第三階段：整理 project shell 與權限邊界

目標：

- 讓 `LayoutRoot` 從「耦合中心」退回單純 shell

執行項：

1. 把登入 UI、權限判斷、staff 跳轉規則拆出 shell
2. 將 shell 對模組 store 的直接依賴降到最低
3. 保留 shell 只做 layout / route 容器角色

完成定義：

- `LayoutRoot` 不再直接呼叫 `login` / `logout` / `loadSession`
- shell 僅保留 layout / route orchestration 責任
- shell 不再直接依賴 staff session 的具體實作細節

完成後可改善到的程度：

- project shell 與模組邊界會更清楚
- 後續再新增 staff 功能時，不必一直把邏輯灌回 `LayoutRoot`

仍無法改善的部分：

- shell 作為 project-level 編排層，仍會保有一定程度的組裝責任

---

## 11. 偏離修正 Gate

本文件不只是分析文件，也作為階段性治理 gate。

規則如下：

1. 每完成一個階段後，必須重新執行一次模組哲學健檢
2. 若仍存在該階段預期應消除的偏離，禁止進入下一階段
3. 若發現新偏離，必須先分類為：
   - 本階段必修正
   - 下一階段處理
   - 合理耦合，不列為偏離
4. 不得以「功能已完成」作為跳過 gate 的理由

這條 gate 的目的，是避免重構過程再次把偏離延後到下一輪，最後累積成新的結構債。

## 12. 可改善到哪種程度

### 可以改善到的程度

若依上述三階段執行，dineCore 可以改善到：

- 明確假模組被移出 `modules/`
- staff 功能不再直接打穿彼此 store
- 顧客流程模組之間不再直接依賴彼此具體內部狀態
- project shell 從耦合中心降回 layout / orchestration 層

也就是可以達到：

> 模組之間主要透過 world / project-level 能力邊界互動，  
> 而不是互相直接抓對方內部 store。

### 無法改善到的程度

本專案是流程型產品，不太可能改善到：

- 每個模組都完全彼此無知
- 顧客點餐鏈完全沒有共享狀態
- shell 完全不參與任何流程組裝

這不是單純技術問題，而是產品流程本身就有共享上下文。

因此更務實的目標不是追求「零耦合」，
而是追求：

- 合法耦合
- 可理解耦合
- 可替換邊界
- 不直接依賴他模組內臟

---

## 13. 最後結論

本專案目前最明確偏離原始模組哲學的，不是所有 staff 模組，
而是以下兩個：

1. `staff-auth`
2. `visitor-stats`

其中：

- `staff-auth` 比較像 project-level 共用 session / login adapter
- `visitor-stats` 則直接打穿 `staff-auth` 邊界

顧客端的 `entry/menu/cart/checkout/order-tracker` 雖然耦合偏高，
但仍可視為同一條點餐流程拆出的業務模組；
它們目前的問題比較像「流程狀態沒有抽到更高一層」，而不是模組身分完全錯置。

因此若要對齊原始模組哲學，建議先從 staff 區開始收斂，
再處理顧客流程的共享狀態與 project shell。

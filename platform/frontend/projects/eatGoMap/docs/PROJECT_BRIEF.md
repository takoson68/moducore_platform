# eatGoMap 專案需求與介面整理

## 0. 文件狀態

- 階段：初步需求探索。
- 來源：2026 年 11 月 3 日 HackMD 討論文件、手機介面草稿及後續對話確認。
- 用途：保存目前共同理解，作為後續前端規格、API 契約與里程碑討論基礎。
- 注意：本文件不是最終 API 規格或資料庫設計。

### 目前實作基線

- 已建立 `map-home` 地圖首頁視覺原型與 `/` 公開路由。
- 已呈現搜尋、分類／距離篩選、合成 Marker、地點卡片與底部導覽；搜尋以 Google Places API (New) 查詢店家／地標與地址。
- 收藏清單以 eatGoMap Worker API／D1 為事實來源，D1 僅保存 Place ID；`map-home` Store 經平台 Storage capability 以 Place ID 將地點詳情與使用者自訂欄位／個人日記保存於目前瀏覽器。資料缺漏或超過 30 天時，使用 Place ID 重新查詢並更新。有效快取座標用於收藏 Marker。這是 eatGoMap 暫用 API，日誌頁仍為未開放提示。現行流程依 [`D008_place_id_indexeddb_cache.md`](../decisions/D008_place_id_indexeddb_cache.md)。
- 地圖底圖與店家／地址搜尋已接入 Google Maps JavaScript API 與 Places API (New)；收藏已接入 eatGoMap 暫用 Worker/D1，打卡尚未接入合作方後端 API。

## 1. 產品概念

`eatGoMap` 是供兩位成員私人使用的「美食 × 旅行共享地圖與日誌」。產品以地圖為主要入口，串接以下核心流程：

```text
地圖探索 → 共同收藏 → 個人打卡 → 美食／旅遊日誌
```

整體採手機優先設計，預期可先以響應式 Web 或 PWA 使用；是否包裝成 WebView 或原生 App 留待後續決定。

## 2. 系統合作邊界

### 2.1 前端

- 由前端開發者負責，建立於 ModuCore 的獨立 `eatGoMap` Project。
- 預計使用既有 Vue／Vite 前端 Runtime。
- 負責地圖呈現、手機 UI、狀態投影、互動流程與合作方 API 串接。

### 2.2 後端

- 由合作開發者負責，預計採 PHP，具體框架尚未決定。
- 後端與資料庫部署於合作方的獨立伺服器。
- 後端負責資料持久化、資料合法性與前端所需 API。

### 2.3 交換原則

- 前端只透過 API 與後端交換事實資料，不直接接觸資料庫或後端私有服務。
- 前後端可分開部署，但須確認 HTTPS、CORS、環境 URL、錯誤格式與版本相容性。
- 業務分類原則上放在 query parameter 或 request body；是否需要自訂 header 應由正式 API 契約決定。

## 3. 資訊架構

底部主要導覽暫定三區：

1. `地圖`：探索、搜尋、收藏與打卡的主要入口。
2. `收藏`：查看尚未打卡或想再次前往的共享地點。
3. `日誌`：回顧美食紀錄與旅遊行程。

草稿中的地點操作採 Bottom Sheet，讓使用者不離開地圖即可查看地點、收藏、打卡與照片。

## 4. 地圖首頁

### 4.1 核心內容

- 取得並顯示使用者目前位置。
- 搜尋店家、景點或地址。
- 依美食／旅遊模式、距離與評分篩選結果。
- 在同一張地圖合併外部地點與後端保存的收藏／打卡資料。
- 以不同 Marker 狀態辨識未收藏、已收藏、已打卡與紀錄擁有者。

### 4.2 地點摘要

- 點選 Marker 後顯示名稱、圖片、收藏狀態與打卡入口。
- 使用者可先保存地點基本資料，再於日後新增打卡內容。
- 外部地點需以穩定識別值去重，避免同一地點重複建立。

## 5. 地點詳情與打卡

### 5.1 地點資料

- 外部地點名稱。
- 地址、電話、評分與座標。
- 外部地點識別值。
- 共同收藏狀態與收藏者。

### 5.2 個人打卡

- 打卡者。
- 打卡時間。
- 個人評分。
- 評論。
- 照片。

同一地點可以有不同使用者、不同時間的多筆打卡。打卡紀錄與地點基本資料應分開，避免更新個人內容時覆蓋共享地點。

### 5.3 照片

- 資料庫只保存照片識別資訊、路徑或 URL，不直接存放圖片二進位內容。
- 實體圖片預計存放於物件儲存或其他雲端空間。
- 儲存方案、檔名、存取權限、壓縮、刪除與失敗重試尚待確認。

## 6. 美食與旅遊日誌

### 6.1 美食日誌

- 依日期由新到舊列出美食打卡。
- 可查看地點資訊、個人評分、評論與照片。

### 6.2 旅遊日誌

- 旅程具有標題、日期區間、封面與包含的打卡紀錄。
- 旅程列表依時間由新到舊排序。
- 旅程詳情顯示所包含的景點與美食打卡。
- 足跡依打卡時間或人工排序串接；第一版不代表真實道路導航路線。
- 日期區間可用來推薦候選打卡，但旅程應明確關聯實際納入的打卡紀錄。

## 7. 初步資料概念

- `User`：初期兩個固定使用者識別。
- `Place`：外部地點識別、名稱、地址、座標與必要快照。
- `SavedPlace`：地點、收藏者及收藏時間。
- `CheckIn`：地點、使用者、時間、評分及評論。
- `CheckInPhoto`：打卡照片的儲存識別與顯示資訊。
- `Trip`：標題、日期、封面與旅程資訊。
- `TripCheckIn`：旅程與打卡的明確關聯及排列順序。

以上名稱僅為概念模型，正式欄位、ID 與關聯由前後端 API／資料契約另行裁決。

## 8. 使用者識別

- 初期只供兩位已知成員私人使用，防冒用不是當前問題。
- 第一版可讓使用者選擇頭像或身分，並由前端記住目前使用者。
- 正式帳密、Token、多人會員與權限可以延後，但身分取得方式應集中在單一能力邊界，避免散落在頁面中。

## 9. 建議開發順序

1. 建立手機 UI 骨架與假資料流程。
2. 接入地圖、定位、搜尋與 Marker。
3. 定義地點、收藏與打卡 API 契約。
4. 串接合作方後端，先完成文字型收藏與打卡。
5. 加入照片上傳與失敗處理。
6. 完成收藏列表。
7. 建立旅程及打卡選取／排序。
8. 完成足跡地圖與日誌詳情。
9. 評估 PWA、WebView 或其他手機入口。

## 10. 待確認事項

- 前後端預計維持獨立 Repository；是否另建 `eatGoMap-contracts` 共用契約 Repository，以及採 Submodule、Subtree 或外部連結引用，尚待與後端開發者確認。
- 地圖供應商、計費／配額與金鑰限制方式。
- Google 地點搜尋由前端透過 Maps JavaScript API 的 Places library 呼叫；合作方後端仍負責共享收藏與打卡事實。
- 搜尋結果卡片依 Worker API 回傳並載入 Store 的收藏狀態決定主要操作：未收藏可收藏，已收藏顯示「打卡」；收藏狀態可於不同瀏覽器讀取。打卡尚未串接後端。
- 合作方後端框架、環境、網域、HTTPS、CORS 與自動部署方式。
- API base URL、版本策略、回應 envelope、錯誤格式、日期時區與分頁規則。
- 地點去重、外部資料快照更新與來源失效策略。
- 照片儲存服務、限制、權限、刪除與備份方式。
- 旅程打卡的自動推薦、人工選取與排序規則。
- 身分識別何時升級為正式驗證。
- 類 App 體驗最終採 PWA、WebView 或其他形式。

## 11. 已確認決策

- Google 底圖 POI 點選採 Google 原生資訊窗呈現資訊；確認收藏後，以 Place ID 查詢詳情並保存於本機 IndexedDB。D1 只保存 Place ID；每筆地點本機記錄包含名稱、地址、座標、電話及個人自訂欄位，缺漏或超過 30 天時再查詢更新。Google 資料留存規則仍須依官方條款逐欄確認。詳見 [`D008_place_id_indexeddb_cache.md`](../decisions/D008_place_id_indexeddb_cache.md)。
- 2026-11-05 建立 eatGoMap 收藏 Worker API 與 D1 Staging 目標；和合作方正式 API 分離。D1 是暫用收藏事實來源，合作方 API 契約完成後再替換。

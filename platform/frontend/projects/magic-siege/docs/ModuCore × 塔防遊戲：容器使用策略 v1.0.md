# ModuCore × 塔防遊戲：容器使用策略 v1.0

> 文件定位：記錄已討論的架構方向，供後續設計與 Codex 實作參考。**不是要求立即重構核心的實作命令。**
>
> 對應文件：《塔防遊戲 MVP 企劃書 v1.0》。先以已確定的玩法驗證架構，不為想像中的需求提前建立系統。
>
> 2026-10-22 已依 `moducore_platform` 現有 Game Runtime 校正：以 `Game` 管理入口與每個遊戲實例的私有 Container 為準，不再以額外建立 `GameContainer` 子類為預設方案。

## 1. 目標與原則

這款 2D 塔防遊戲使用 **ModuCore 現有 Game Runtime 與容器模式** 承載遊戲應用，而不是另起爐灶製作一套遊戲框架。

- **沿用既有 Game Runtime**：由 `Game` 組合現有 `Container`、狀態工廠與生命週期，不複製容器邏輯，也不為了形式而新增無實際能力的子類。
- **核心保持通用**：遊戲專屬能力不寫回平台核心，不因塔防而污染其他應用。
- **需求驅動擴充**：只有當確定的玩法需要某項能力時才加入，不預先製作大量 Manager、介面或抽象層。
- **模組反向註冊**：每個遊戲模組負責註冊自己的狀態與功能，容器不預設所有塔防資料欄位。
- **狀態與畫面分離**：畫面每幀重新繪製，不代表生命值、金幣、怪物等資料要每幀重新建立。
- **維持 OOP 思路**：物件持有自己的屬性與狀態；共通規則由適當的通用能力處理。

## 2. 既有 ModuCore 的角色分工

| 元件 | 既有定位 | 在塔防中的使用原則 |
| --- | --- | --- |
| `world.js` | 平台入口／啟動協調，整合 boot、router、API 等 | 繼續擔任平台角色；**不**作為遊戲容器的繼承基底 |
| `src/app/container/container.js` 的 `Container` 類別 | 通用容器：註冊工廠、解析與快取實例等 | 由 `createGameContainer()` 建立每個遊戲實例的私有容器 |
| `src/app/container/index.js` | 現有平台單例容器的使用入口／適配層 | 不把它當成新的遊戲類別來繼承 |
| `src/game.js` 的 `Game` 類別 | 遊戲管理入口；組合私有容器、狀態工廠與生命週期 | 每局建立一個 `Game` 實例，由它處理啟動、暫停、恢復、重開與卸載 |
| `src/app/game/container.js` | 建立、註冊與銷毀遊戲私有 Container | 塔防模組只宣告自己的 stores 與 services，不直接使用平台單例 |
| `boot` | 啟動與組裝 | 遵循既有流程，按實際需要接入遊戲 |
| 遊戲模組 | 場景、玩法與各自資料 | 自行向遊戲容器註冊需要的能力 |
| `pages`／場景 | 使用者看見並操作的遊戲畫面 | 對應不同遊戲場景；場景與共用模組分開 |

> 以上是責任界線，不代表要現在新增所有目錄或檔案。

## 3. 核心決策：沿用現有 Game 與私有 Container

目前已實作且經遊戲測試驗證的方向是：

```js
import Game from '@/game.js'

const game = new Game()
await game.start({ modules: [towerDefenseModule] })
```

每個 `Game` 實例內部都有獨立 Container。模組透過 `setup.stores` 與 `setup.services` 反向註冊能力；`Game` 依序執行 `init`、`start`、`pause`、`resume`、`stop` 與 `dispose`。

### 為什麼不再建立 GameContainer 子類？

現有 `Game` 已組合塔防 MVP 所需的容器隔離、延遲解析、實例管理、操作排隊與清理邏輯。目前沒有只能由子類提供的額外遊戲共通能力，因此新增空殼繼承層只會增加概念與維護成本。未來若出現明確需求，再以最小變更擴充，不在 MVP 預設。

### 為什麼不讓 `world.js` 繼承遊戲？

`world.js` 目前是平台層協調入口，並不是通用容器基底。將遊戲邏輯混入平台 World，會模糊責任，也讓非遊戲專案承擔不必要的耦合。

## 4. 反向註冊：狀態屬於模組，不屬於容器預設清單

**不要**在 `Game`、`createGameContainer()` 或平台 Container 中預先塞入 `hp`、`coins`、`enemies`、`towers`、`wave` 等欄位，因為這些是「塔防遊戲的需求」，不是所有遊戲容器都必備的能力。

建議由各模組自行定義與註冊，例如：

| 遊戲模組（概念） | 自己負責的資料與規則 |
| --- | --- |
| 基地 | 基地生命值、受到突破傷害、敗北判定 |
| 經濟 | 金幣餘額、戰鬥期間被動收入、擊殺獎勵、花費與退費 |
| 砲塔 | 建造、升級、拆除、目標鎖定、攻擊冷卻 |
| 敵人 | 個別怪物的血量、速度、位置、死亡與抵達終點 |
| 波次 | 10 波配置、出怪進度、準備／戰鬥階段、過關判定 |
| 地圖 | 格子資料、道路、障礙、可建造與佔用狀態 |
| 子彈 | 飛行、追蹤、命中與失效 |

這張表是**責任劃分參考**，不是要求每一列都建立獨立的類別、Manager 或檔案。以最少可用模組落地即可。

## 5. 長期存在的資料與每幀繪製

遊戲畫面（例如使用 p5.js）可能每幀清除畫布並重新繪製，但**遊戲資料不應跟著每幀重建**。

概念上的循環：

1. 啟動時建立 `Game` 實例，由它建立私有容器，再註冊並取得需要的模組／物件。
2. 玩家開始波次，遊戲物件依時間推進狀態。
3. 敵人位置、血量、砲塔冷卻、金幣、基地生命等資料持續存在。
4. 畫面從目前狀態讀取資料並繪製。
5. 波次結束後，保留需要跨波次存在的資料（砲塔、金幣、基地生命），清理該波已完成的臨時物件。

**容器負責組織與取得長期存在的能力／狀態；繪圖工具負責呈現。** 不需要讓容器直接負責每個像素的繪製。

## 6. 物件與個別屬性：怪物速度可調整

已確認：**小怪快而脆、大怪慢而耐打**；但每隻怪物的速度與血量應可個別調整，不能寫死在整個遊戲的移動規則中。

```js
// 僅示意資料形狀，非正式數值
const smallEnemy = { hp: 50, speed: 2, reward: 5, baseDamage: 1 }
const bigEnemy = { hp: 200, speed: 0.8, reward: 20, baseDamage: 3 }
```

需區分：

- **類型預設值**：定義某種怪物的初始速度、血量與獎勵。
- **個別實例狀態**：每隻怪物自己的當前血量、位置、速度等。

目前 10 波難度主要透過**數量與大怪比例**增加，不要求每波自動提升怪物速度或血量；但保留未來逐隻調整的彈性。

## 7. 遊戲場景與共用模組

先前討論的對應方式是：

- **場景**可以理解為遊戲中的 `pages`，例如遊戲主畫面；是否需要更多場景，以 MVP 需求為準。
- **共用能力**（例如跨場景仍須保留的資料或工具）可從場景抽離，避免場景切換時遺失狀態。
- **模組與場景分離**：場景使用模組，不直接擁有整個遊戲的長期資料生命週期。

第一版只有一張固定地圖，不需要先做通用場景管理器或地圖編輯器。

## 8. 容器實例與隔離原則

目前一次只運行一款遊戲，**先使用一個 `Game` 實例**即可，不額外建立多遊戲管理系統。

現有 `createGameContainer()` 以空的 services 建立新 `Container`，不沿用平台單例的 service 實例。遊戲狀態與能力應繼續只注入這個私有容器；若未來需要 storage 或 event bus，必須由遊戲模組明確註冊並定義清理責任，不預設與平台共用。

## 9. 已驗證的平台基線與塔防待驗證項目

**已由現有原始碼與 `test:game` 範圍驗證：**

1. `Game` 實例各自持有私有 Container，不將遊戲 store 註冊至平台容器。
2. stores 與 services 可由模組反向註冊、延遲解析與快取。
3. 生命週期依序啟動，並以反向順序停止與清理。
4. `reset()` 會清理舊實例並以原模組宣告重新啟動；`dispose()` 會釋放資源與模組宣告。

**塔防 MVP 實作後仍需驗證：**

1. 跨幀、跨波次資料是否保留正確，重開是否完整清除遊戲狀態。
2. 暫停後的敵人、子彈、砲塔冷卻、出怪與收入計時是否一致停止。
3. 遊戲模組的責任邊界是否清楚，且沒有為未確定需求引入額外抽象。
4. 新增資源、計時器與事件監聽是否都由所屬模組正確釋放。

## 10. 明確不在第一版預先實作的項目

- 重新發明一套獨立的 Container。
- 把塔防專屬欄位或功能塞進平台核心。
- 多遊戲切換管理器、通用遊戲引擎框架。
- 動態地圖編輯器、隨機地圖、多場景系統。
- 尚無需求支撐的大量抽象介面、Manager 或繼承層級。

## 11. 與遊戲企劃的關係

遊戲玩法以《塔防遊戲 MVP 企劃書 v1.0》為準：固定格子地圖、單一路線、可建造／升級／拆除砲塔、追蹤子彈、最近敵人優先、大小怪、10 波、戰鬥中收入與操作、基地生命值 20、守住第 10 波勝利。

**這份文件回答「如何利用 ModuCore 承載已確定的玩法」，而不是反過來要求玩法配合某個預想架構。**
